gotto-hando --help-windows - Windows: interactive session, session bridge
(Task Scheduler), SmartScreen, UAC/UIPI, DPI, cmd /C and code pages.

== WHEN YOU NEED THIS ==
  `gotto-hando local qinfo` shows session=locked|inactive; a run exited 4
  with E_SESSION; input is accepted (ok) but an elevated app does not
  react; you are about to drive a Windows PC over ssh (`gotto-hando
  --bridge` must run there); exec output looks like mojibake.

== CHECK ==
  $ gotto-hando local qinfo
  os=windows osver=10.0.22631 arch=amd64 ver=1.2.3 primary=ctrl
  desktop=0,0 2560x1440 displays=1 session=active perms=n/a elevated=0
  (one line in reality; wrapped here)
  session=active    this process is in the active console session and the
                    input desktop is "Default": input and capture work.
  session=bridge    this process was started by ssh (or is outside the
                    console session) and the answer came through the
                    logged-on session's `gotto-hando --bridge`: runs work.
  session=locked    the input desktop is Winlogon: lock screen, UAC secure
                    desktop, Ctrl+Alt+Del screen. Unlock / dismiss.
  session=inactive  an answering GUI/backend diagnostic can report that its
                    session became unusable, for example after a disconnected
                    RDP or non-active GUI session. An ssh-started query-only
                    run without a reachable bridge aborts E_SESSION, exit 4;
                    start `gotto-hando --bridge`.
  perms=n/a         Windows has no permission dialogs for input/capture.
                    Nothing to grant. `--request-perms` is exit 2 on
                    Windows, locally (usage error) and through a <dest>
                    (abort E_VALIDATE after the start object).
  elevated=0|1      whether the answering process (the bridge, when
                    session=bridge) runs as Administrator (UIPI, below).
  Preflight also rejects a run while a key or mouse button is physically
  held down (GetAsyncKeyState over every virtual key): release it and
  retry (E_INPUT, exit 4). Preflight checks only what the run contains and
  the held-key guard protects input injection, so a run of only qinfo qdisp
  qmouse sleep set and comments never fails it or the session check (it
  reports session=); every other command needs the active, unlocked session
  or the bridge (help.txt EXECUTION step 4).

== INTERACTIVE SESSION REQUIRED ==
  SendInput and screen capture only work from a process inside the
  logged-on user's interactive desktop.
    - NOT a Windows service / session 0 (always E_SESSION). Do not wrap the
      bridge in a service (sc.exe, NSSM, srvany).
    - NOT a locked desktop: the lock screen, a screen saver with password,
      or a UAC prompt switch the input desktop to Winlogon
      (session=locked). Disable automatic lock while driving: Settings >
      Accounts > Sign-in options > "Require sign-in: Never", and Power &
      sleep / screen timeout: Never. Autologon (netplwiz / Sysinternals
      Autologon) restores the session after a reboot.
    - RDP: while you are connected over RDP the RDP session is the active
      one; DISCONNECTING locks it (session=inactive/locked). To hand the
      desktop back to the physical console without locking it, run from
      inside the RDP session (elevated):
        tscon %SESSIONNAME% /dest:console
      Then keep the console unlocked (settings above). A headless PC
      without a monitor may need a dummy HDMI/DP plug so that a display
      exists to capture (otherwise cap fails with E_CAPTURE).
    - SSH (OpenSSH Server) shells are session 0: a `gotto-hando local`
      started over ssh cannot drive the desktop itself and hands the run
      to the bridge (next section). That is the ONLY way a <dest> run
      reaches a Windows desktop.

== SESSION BRIDGE FOR SSH (TASK SCHEDULER) ==
  Why: every `gotto-hando <dest> ...` becomes `ssh <dest> gotto-hando
  local ...` on this PC, and sshd starts it in session 0. Such a process
  detects that it is remote (SSH_CONNECTION / SSH_TTY set, or its session
  id != WTSGetActiveConsoleSessionId, or WinSta0 not accessible) and
  forwards the IR over a named pipe to `gotto-hando --bridge`, a normal
  process of the logged-on user that does the actual preflight, input and
  capture. Without a running bridge the run fails in preflight with
  E_SESSION (exit 4) and the hint "start `gotto-hando --bridge` in the
  logged-on GUI session". Running the bridge is therefore the user's
  consent to remote control, and quitting it (End task, Ctrl-C) is the kill
  switch. The pipe \\.\pipe\gotto-hando-<username> has an ACL for the
  current user only and is not reachable from the network; protocol
  details are in --help-remote SESSION BRIDGE.
  A `gotto-hando local` typed into a terminal window on this PC never uses
  the bridge, whether or not one is running.
  Start it for a quick test from any window in the logged-on session:
    gotto-hando --bridge
  Register it to start at logon (recommended):
    GUI: Task Scheduler > Create Task
      General:    "Run only when user is logged on"  (REQUIRED - "whether
                  user is logged on or not" has no interactive desktop)
                  "Run with highest privileges" only if you need to drive
                  elevated apps (UIPI, below)
      Triggers:   At log on - specific user
      Actions:    Start a program: C:\tools\gotto-hando.exe
                  Arguments: --bridge
      Conditions: uncheck "Start the task only if the computer is on AC
                  power"
      Settings:   uncheck "Stop the task if it runs longer than";
                  "If the task is already running: Do not start a new
                  instance"
    Command line equivalent (interactive-only task for the current user):
      schtasks /Create /TN gotto-hando-bridge /SC ONLOGON /RL LIMITED /F ^
        /TR "\"C:\tools\gotto-hando.exe\" --bridge"
      schtasks /Run /TN gotto-hando-bridge   # start now without logging off
      schtasks /End /TN gotto-hando-bridge   # kill switch
      (use /RL HIGHEST from an elevated prompt for an elevated bridge)
  When started without a console (Task Scheduler) the bridge shows no
  window; started from a terminal it stays in the foreground until Ctrl-C.
  It logs one line per run and error to
  %LOCALAPPDATA%\gotto-hando\bridge.log (no sequence contents, no images)
  and writes nothing else to disk. A second bridge for the same user exits
  2. It is the same binary; there is no separate windowsgui build.
  A startup-folder shortcut (shell:startup) also works but cannot be
  elevated without a UAC prompt at every logon.
  Verify from the controlling machine:
    gotto-hando <dest> qinfo     -> session=bridge perms=n/a elevated=0|1

== SMARTSCREEN AND DEFENDER ==
  A binary downloaded with a browser carries the Mark-of-the-Web; on first
  start SmartScreen shows "Windows protected your PC". A person must click
  "More info" > "Run anyway" (cannot be automated), or remove the mark
  beforehand:
    powershell -NoProfile -Command "Unblock-File C:\tools\gotto-hando.exe"
  A binary built locally with `go build` has no mark. Defender occasionally
  flags unsigned Go binaries as a false positive (Trojan:Win32/Wacatac
  etc.): add the folder to Windows Security > Virus & threat protection >
  Exclusions, or use a locally built binary. There is no code-signing
  requirement for input/capture.

== UAC AND ELEVATED APPS (UIPI) ==
  While a UAC elevation prompt is showing, Windows switches to the secure
  desktop: session=locked, nothing can be driven and captures fail.
  gotto-hando cannot click "Yes" for you; a person dismisses it (or the
  app is started elevated beforehand).
  Apps running as Administrator ignore SendInput from a non-elevated
  process (UIPI). The OS reports success, so gotto-hando prints `ok` and
  the app does nothing; this cannot be detected. Check `qinfo` elevated=;
  to drive elevated apps run the executing process elevated: an elevated
  terminal for `local`, an elevated bridge for ssh (Task Scheduler "Run
  with highest privileges" / `schtasks /RL HIGHEST`). An elevated process
  can drive both kinds.

== DPI AND COORDINATES ==
  Coordinates are physical pixels. gotto-hando declares Per-Monitor-V2 DPI
  awareness (manifest + SetProcessDpiAwarenessContext), so it sees real
  pixels on every monitor regardless of the scaling percentage, and a
  default `cap` (scale=1) is pixel-exact: a position found in the PNG is
  the coordinate to click. `qdisp` lists each monitor's origin, size and
  scale (1.25 = 125%).
  Virtual-desktop origin is the top-left of the PRIMARY monitor; monitors
  to the left/above have negative coordinates.
  `qwin` lists top-level windows that are visible, not cloaked (DWM), have
  a non-empty title and are not tool windows. Frames are the DWM extended
  frame bounds, i.e. they exclude the invisible drop-shadow border.
  An app that is NOT DPI-aware is bitmap-stretched by Windows; its own
  notion of coordinates differs, but what you see in `cap` is what
  SendInput hits, so always take coordinates from a capture.
  Window captures use PrintWindow, which works even when the window is
  covered; some GPU-rendered apps come out black - use a desktop or rect
  capture then.

== exec ON WINDOWS ==
  exec[]prog args...   direct: the payload is split on spaces ("..."
                       quoting only) and run as a process.
  exec[shell]...       `cmd /C <payload>`: pipes, redirection, built-ins
                       (dir, copy, set), wildcards via the command. It is
                       always cmd; for PowerShell call it explicitly:
                         exec[]powershell -NoProfile -Command Get-Process
  Output encoding: cmd and many console programs write the OEM code page
  (CP437, CP949, ...). gotto-hando decodes stdout/stderr with the console
  output code page (GetConsoleOutputCP; the ANSI code page GetACP when the
  executing process has no console, e.g. a Task Scheduler-started bridge)
  and delivers UTF-8. Undecodable bytes become U+FFFD. gotto-hando never
  forces chcp 65001 itself. If a program prints UTF-8 while the console is
  CP949, switch the code page in the same command:
    exec[shell]chcp 65001 >nul && type file.txt
  PATH: a Task Scheduler-started bridge has the user's normal PATH (unlike
  macOS launchd). Absolute paths are still safest.
  Paths with spaces:
    exec[]"C:\Program Files\Blender\blender.exe" --version
  (no backslash escaping in exec; "..." only groups words).

== CAVEATS ==
  CAVEAT: SetForegroundWindow may only flash the taskbar button. `win`
          retries with input-thread attachment and a synthetic Alt tap and
          reports E_NOWINDOW if the window still did not come to the
          front. Retry once; then click it (c[]x,y).
  CAVEAT: Unicode text injection (txt) is ignored by scan-code apps
          (Blender, games, Win32 consoles). Use k per key or paste.
  CAVEAT: Keypad keys are sent by scan code (physical position) regardless
          of NumLock; use numpad0-9 / numenter deliberately. Arrow, Home/
          End, Insert/Delete, Page keys, Win and right Ctrl/Alt are sent as
          extended keys; every key carries its scan code so DirectInput
          apps see it.
  CAVEAT: Win32 console windows do not accept Ctrl+V paste by default: use
          clip[] + k[s]insert or right-click, or exec instead.
  CAVEAT: Store/UWP apps and some games running in exclusive fullscreen
          may not honour synthetic input; verify with cap.
  CAVEAT: txt sends UTF-16 units (surrogate pairs in order); a per-
          character ms= gap applies per Unicode character.
  CAVEAT: scroll[by=page] sends the same wheel notches as by=line - Windows
          has no pixel/page-unit wheel injection API, only WHEEL_DELTA
          notches interpreted by the receiving app using the user's own
          "lines to scroll" setting.
  CAVEAT: The bridge runs with the privileges of the logged-on user (or
          Administrator when registered with highest privileges). exec via
          a <dest> runs with exactly those privileges; there is no
          allowlist (--help-remote SECURITY MODEL).
