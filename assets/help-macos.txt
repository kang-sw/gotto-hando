gotto-hando --help-macos - macOS: signing, permissions (TCC), sessions,
session bridge for ssh, displays.

== WHEN YOU NEED THIS ==
  `gotto-hando local qinfo` shows perms=accessibility:missing or
  screen:missing, or session=locked|inactive; a run exited 4 with
  E_PERMISSION / E_SESSION; you rebuilt the binary and input stopped
  working; you are about to drive a Mac over ssh (`gotto-hando --bridge`
  must run there, with permissions).

== CHECK ==
  $ gotto-hando local qinfo
  os=darwin osver=14.5 arch=arm64 ver=0.1.0 primary=cmd desktop=0,0 2560x1440
  displays=2 session=active perms=accessibility:ok,screen:ok
  (one line in reality; wrapped here)
  perms=accessibility:*  gates input (k kd ku txt m c md mu drag scroll
                         paste) and window control (win, open[wait=]). Read
                         with AXIsProcessTrusted() by the process that will
                         inject: this one, or the bridge when
                         session=bridge.
  perms=screen:*         gates cap only. Without it qwin and win still run
                         (status ok) but window titles come back empty, and
                         qinfo reports screen:missing. Read with
                         CGPreflightScreenCaptureAccess().
  session=active         this process is in the GUI (Aqua) session,
                         unlocked. bridge = this process was started by ssh
                         and the answer came through the GUI session's
                         `gotto-hando --bridge`: runs work. locked = lock
                         screen / screen saver. inactive = not a GUI
                         session (ssh) and no bridge running: nothing can
                         run (E_SESSION).
  qinfo never prompts. Preflight checks only what the run contains: a run
  of only qinfo qdisp qmouse sleep set and comments never fails on session
  or permissions (it reports them); every other command needs an unlocked
  GUI session, own or bridge (else E_SESSION, exit 4); the commands listed
  under accessibility need it and cap needs Screen Recording (else
  E_PERMISSION, exit 4); clip qclip exec open (without wait=) need no
  permission.

== LOCAL BUILD AND RUN ==
  `go build` / `go install` / `git clone` + build: the Go linker ad-hoc
  signs the binary; that is all a local binary needs. Such binaries carry
  no quarantine attribute and start normally.
  A binary DOWNLOADED with a browser is quarantined and blocked ("cannot be
  opened", "not verified"). Remove the attribute:
    xattr -d com.apple.quarantine ./gotto-hando
  Notarization is NOT needed for this tool (it requires a paid Apple
  Developer Program membership). Do not chase it.

== WHO OWNS THE PERMISSION (RESPONSIBLE PROCESS) ==
  TCC attributes a permission to the "responsible" app of the process.
  When gotto-hando runs from a terminal application (Terminal, iTerm2, the
  VS Code integrated terminal, ...) that app is responsible: the toggle
  you see in System Settings is for Terminal/iTerm2/Code, not for
  gotto-hando. Consequences:
    - Local use (`gotto-hando local ...` typed into a terminal): grant the
      permission ONCE to the terminal app. Rebuilding gotto-hando does not
      affect it. Nothing else to do.
    - `gotto-hando --bridge` started from a Terminal window: same thing -
      the terminal app's grant covers the bridge and every ssh run it
      serves. Simplest remote setup; the window must stay open.
    - `gotto-hando --bridge` started by launchd (LaunchAgent): the binary
      itself is responsible, so the permission is bound to the binary's
      code-signing identity (next section) and must be granted on that Mac
      by hand (SESSION BRIDGE FOR SSH below).
  An agent running INSIDE a terminal-hosted tool inherits that terminal's
  grant. A process started by sshd has no GUI session at all; it never
  gets permissions and never injects - it goes through the bridge.

== STABLE SIGNING IDENTITY (SURVIVING REBUILDS) ==
  TCC binds a grant to the code-signing identity. An ad-hoc signature has
  no identity - its designated requirement is the hash of that exact build
  - so every rebuild is a new "app" and the grant is lost (even with a
  fixed --identifier).
  Fix: sign with a self-signed code-signing certificate, which gives the
  binary a stable identity across rebuilds.
    1. Keychain Access > Certificate Assistant > Create a Certificate...
       Name: gotto-hando-dev   Identity Type: Self Signed Root
       Certificate Type: Code Signing   -> Create.
    2. After every build:
       codesign -s "gotto-hando-dev" --force ./gotto-hando
       codesign -dv ./gotto-hando     # shows Authority=gotto-hando-dev
    3. Put step 2 in your Makefile / build script (the repo's
       scripts/codesign-dev.sh does this). Grant the permission once per
       Mac for this identity; later rebuilds keep it.
  This matters only where the binary itself is the responsible process
  (the bridge under a LaunchAgent). For terminal use - including a bridge
  started from a terminal window - the terminal app's grant covers you and
  this step is optional.
  A binary re-signed with a different certificate (or ad-hoc again) is a
  new identity: grant again.

== GRANTING PERMISSIONS: PROCEDURE ==
  Do this in order; stop as soon as qinfo shows ok. Only a human can flip
  the toggles - steps 3-4 cannot be automated.
    1. gotto-hando local qinfo          # which of accessibility / screen
                                        # is missing? (remote Mac:
                                        # gotto-hando <dest> qinfo)
    2. gotto-hando local --request-perms
       Asks macOS to show the permission prompts. Remote Mac:
       `gotto-hando <dest> --request-perms` - the BRIDGE on that Mac
       calls the same APIs, so the prompts appear on that Mac's screen
       (no bridge: E_SESSION, exit 4).
       - Calls AXIsProcessTrustedWithOptions(prompt=true) and
         CGRequestScreenCaptureAccess(). Prints the same perms= line as
         qinfo and exits 0 when both are ok, 4 otherwise.
       - The prompt ADDS the responsible app to the list in System
         Settings but does not turn it on; a person must toggle it.
       - Screen Recording takes effect only after the process is
         RESTARTED (quit the terminal tab, or restart the bridge).
       - On Windows: exit 2, locally and through a <dest>.
    3. Tell the user exactly this:
         System Settings > Privacy & Security > Accessibility
           -> enable <Terminal app | gotto-hando>
         System Settings > Privacy & Security > Screen Recording
           -> enable <Terminal app | gotto-hando>
       If the entry is absent, press "+" and choose the binary (for a
       LaunchAgent bridge) or the terminal app. Then restart gotto-hando /
       the bridge. (macOS 15+ may re-confirm Screen Recording
       periodically; same toggle.)
    4. Re-run step 1. If accessibility is still missing after toggling,
       the identity changed (rebuild without a stable signature): remove
       the stale entry with "-" and add the binary again, or
       `tccutil reset Accessibility` and redo.
  `tccutil reset Accessibility|ScreenCapture [<bundle-id>]` only CLEARS
  grants; it cannot grant.
  MDM (PPPC profile) can pre-approve Accessibility but cannot pre-approve
  Screen Recording - that one is always a manual toggle.

== SESSION BRIDGE FOR SSH (REMOTE MAC) ==
  Why: every `gotto-hando <dest> ...` becomes `ssh <dest> gotto-hando
  local ...` on this Mac. A process started by sshd is outside the Aqua
  (GUI) session: events posted from it are dropped, captures are blank and
  TCC never prompts for it. Such a process detects that it is remote
  (SSH_CONNECTION / SSH_TTY in its environment) and forwards the IR over a
  unix socket to `gotto-hando --bridge`, a process the user runs INSIDE the
  GUI session, which does the actual preflight, input and capture. Without
  a running bridge the run fails in preflight with E_SESSION (exit 4) and
  the hint "start `gotto-hando --bridge` in the logged-on GUI session".
  Running the bridge is therefore the user's consent to remote control,
  and quitting it is the kill switch. The socket
  $HOME/Library/Application Support/gotto-hando/bridge.sock (0600, dir
  0700) is same-machine, same-user only; protocol: --help-remote SESSION
  BRIDGE. A `gotto-hando local` typed into a terminal on this Mac never
  uses the bridge, whether or not one is running.
  Start it, in one of two ways:
    - Interactive: in a Terminal window on that Mac (or via Screen
      Sharing) run
        gotto-hando --bridge
      and leave the window open. Permissions are Terminal's (RESPONSIBLE
      PROCESS): grant Accessibility and Screen Recording to Terminal once;
      no signing needed.
    - Unattended: a LaunchAgent (runs in the user's GUI session, restarts
      at login). Permissions then belong to the BINARY: sign it with the
      stable identity first (above).
        ~/Library/LaunchAgents/io.gotto-hando.bridge.plist
        <?xml version="1.0" encoding="UTF-8"?>
        <!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
          "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
        <plist version="1.0"><dict>
          <key>Label</key><string>io.gotto-hando.bridge</string>
          <key>ProgramArguments</key><array>
            <string>/usr/local/bin/gotto-hando</string>
            <string>--bridge</string></array>
          <key>RunAtLoad</key><true/>
          <key>KeepAlive</key><true/>
          <key>LimitLoadToSessionType</key><string>Aqua</string>
        </dict></plist>
        launchctl bootstrap gui/$(id -u) \
          ~/Library/LaunchAgents/io.gotto-hando.bridge.plist
        launchctl kickstart -k gui/$(id -u)/io.gotto-hando.bridge
          # restart after a permission change or rebuild
        launchctl bootout gui/$(id -u)/io.gotto-hando.bridge
          # kill switch: remote control impossible until bootstrapped again
  The bridge logs one line per run and error to
  ~/Library/Logs/gotto-hando/bridge.log (no sequence contents, no images)
  and writes nothing else to disk. A second bridge for the same user exits
  2.
  Grant permissions to the bridge's responsible process (Terminal, or the
  binary) by a person at the machine or over Screen Sharing: System
  Settings > Privacy & Security > Accessibility and Screen Recording > "+"
  > select it. Shortcut without Screen Sharing - pop the prompts on that
  Mac's screen from your machine:
    gotto-hando <dest> --request-perms
  The bridge calls AXIsProcessTrustedWithOptions / CGRequestScreenCapture-
  Access in its own GUI session, so the system prompts appear there. The
  prompt adds the app to the lists but a person at that Mac still has to
  flip the toggles, and Screen Recording is picked up only after the bridge
  restarts (`launchctl kickstart -k ...`, or Ctrl-C and run again). Then
  verify from your machine:
    gotto-hando <dest> qinfo
      -> session=bridge perms=accessibility:ok,screen:ok
  Keep the Mac awake and unlocked while it is being driven:
  `caffeinate -d -i` in another LaunchAgent, or System Settings > Lock
  Screen > never require password / never turn display off. A locked or
  sleeping Mac reports session=locked (exit 4).
  PATH, two separate issues:
    - Finding gotto-hando itself: sshd runs the remote command with a
      minimal PATH (/usr/bin:/bin:/usr/sbin:/sbin plus ~/.zshenv). If
      `ssh <dest> gotto-hando --version` says "command not found", install
      into such a directory, extend PATH in ~/.zshenv, or pass
      `--remote-bin /usr/local/bin/gotto-hando` (--help-remote).
    - exec inside a run: exec[]cmd uses the bridge's PATH, which under
      launchd is reduced; exec[shell] runs the login shell (`$SHELL -lc`)
      whose rc files restore PATH. Prefer exec[shell] or absolute paths.
  Remote install, ssh config and troubleshooting: --help-remote.

== SESSION, LOCK, SECURE INPUT ==
  session=locked    lock screen or screen saver is up. Input and capture
                    fail in preflight (exit 4). Unlock; prevent with
                    caffeinate.
  session=inactive  the process is not in the GUI session (ssh) and no
                    bridge is running. Start `gotto-hando --bridge` in the
                    GUI session (above).
  Secure Input      while a password field (or an app that enables Secure
                    Event Input) is focused, synthetic key events are
                    blocked. The failing line reports E_INPUT with a hint.
                    Click elsewhere / close the dialog and retry.
  Fast user switching: only the session that owns the console can be
  driven; a bridge of a switched-away user reports session=inactive.

== DISPLAYS AND COORDINATES ==
  Coordinates are in points (logical). On Retina displays one point = 2
  pixels (scale=2 in `qdisp`); a default `cap` is downscaled so image
  pixels == points, and you can feed pixel positions from the PNG straight
  back as coordinates.
  cap[scale=native] keeps full pixels - divide by the display's scale
  before using them as input coordinates.
  Multi-display: origin (0,0) is the top-left of the primary display;
  displays to the left/above have negative coordinates. Displays can have
  different scales; `qdisp` lists idx, origin, size and scale, and
  m[disp=N] / cap[disp=N] address one display.
  `qwin` frames include the title bar; c[w]x,y is relative to the window's
  top-left INCLUDING the title bar. qwin lists the layer-0 windows of apps
  with a regular activation policy (no menu bar, dock, desktop elements or
  background agents), minimized (min) and hidden-app (hidden) windows
  included; `win` searches the same list, so a minimized match is found and
  restored.

== CAVEATS ==
  CAVEAT: Rebuilt and input stopped? qinfo -> perms missing -> the identity
          changed. Use the self-signed certificate step or, for terminal
          use (and a terminal-started bridge), nothing at all (the
          terminal app owns the grant).
  CAVEAT: `open[]Name` uses `open -a Name` (bundle name, case-insensitive);
          a path uses `open <path>`. A wrong name is E_EXEC.
  CAVEAT: exec[shell] runs `$SHELL -lc` (zsh by default): your ~/.zprofile
          / ~/.zshrc PATH applies, even when the bridge runs under launchd.
  CAVEAT: k[]a etc. are physical US-layout keys; with a non-US or IME input
          source use txt for text. txt uses Unicode key events and bypasses
          the IME in most apps.
  CAVEAT: Some apps only honour modifier flags carried on the event, not
          separate modifier key-downs; gotto-hando sets both. If a chord is
          ignored, try the k[]ctrl+shift+a form vs k[cs]a and verify with
          cap.
  CAVEAT: Double clicks are sent with the click-state field set (c[n=2]);
          two separate `c` lines are NOT a double click.
  CAVEAT: The key names volup, voldown and mute cannot be produced on
          macOS; a line using them fails in preflight (E_INPUT, exit 4).
